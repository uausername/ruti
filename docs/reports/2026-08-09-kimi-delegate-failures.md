# Отчёт: `ruti delegate --model kimi` ненадёжен через `opencode`

**Дата**: 2026-08-09
**Окружение**: `ruti` 2.0.0, `opencode` 1.18.13, прокси LiteLLM на `127.0.0.1:4000`,
модель прокси `kimi` → `openai/moonshotai/kimi-k3-free` (удалённая, без расхода
подписки). Windows 11, `C:\Users\Lenovo Gaming\AppData\Local\ruti\logs\`.

## Итог

За одну сессию `kimi` через `ruti delegate` / `opencode run` три раза подряд
не выполнила задачу тремя разными способами: зависание без вывода, зависание
с явным килом по таймауту, успешное завершение с пустым/потерянным телом
задачи. Во всех трёх случаях `substituted: false` — это не проблема
фолбэка на другого провайдера, а проблема самой связки `opencode run
--model ruti-router/kimi` (или того, как `ruti` её вызывает).

## Случай 1 — полное зависание без вывода (проект ComDig)

```
ruti delegate --model kimi --dir "C:\mycode\comdig" --timeout 300 --json \
  --task "Ознакомься с этим проектом: изучи структуру репозитория, ..."
```

- `duration_s`: 373.4 (таймаут 300 истёк, `ruti` убила процесс ещё через ~73с)
- `error`: `"C:\...\opencode.CMD did not finish within 300s and was killed"`
- `exit_code`: -1, `files_changed`: [], `substituted`: false
- Лог-файл **не был создан вообще** — `C:\...\ruti\logs\delegate-20260809-133415-...log`
  отсутствует на диске (только сопутствующий `task-20260809-133415.md` с
  текстом задачи). То есть `opencode` не вывел в stdout/stderr ни строчки за
  300+ секунд — завис до первого обращения к модели (вероятно на индексации
  репозитория; в директории `.git/objects` тысячи файлов + JSON ~1MB
  (`comments.json`)).

## Случай 2 — успешное завершение, но пустое тело задачи (та же задача, сужена)

Тот же проект, но задача сужена до 2 файлов и передана через `--task-file`
вместо `--task`:

```
ruti delegate --model kimi --dir "C:\mycode\comdig" --timeout 600 --json \
  --task-file cleanup_brief.md
```

- `exit_code`: 0, `duration_s`: 17.9, `substituted`: false,
  `model_answering`: "kimi" (реально отвечала запрошенная модель)
- `files_changed`: [], `lines_written`: 0 — **ничего не сделано**
- Файл `task-20260809-144644.md`, который `ruti` фактически записала на
  диск, содержит **полный корректный бриф** (~4000 символов, весь текст
  задачи присутствует).
- Но в логе `opencode` модель отвечает так, будто получила почти пустое
  сообщение:

  ```
  Body seems empty. User's message references "two specific files" but
  doesn't name them. I need to ask for clarification before diving in...
  ```

  Модель ни разу не называет `fix_parent_ids.py` или
  `PROJECT_FILES_DOCUMENTATION.md` — то есть контент из `--task-file` до неё
  не дошёл, хотя на диск он был записан верно. Значит проблема — в передаче
  содержимого файла в сам вызов `opencode run` (аргумент CLI, stdin, или то,
  как `ruti` строит промпт из `task-file`), а не в содержимом брифа.

## Случай 3 — зависание с явным килом по маленькому таймауту (не ComDig)

Найден в тех же логах, другая, несвязанная задача (видимо, более ранний
тест интеграции самой `ruti`):

```
task: "Read every Python file in ruti/ carefully and write a one-paragraph
       summary of the whole architecture to ARCHITECTURE_SUMMARY.md"
```

- Лог `delegate-20260809-135417-ruti-router_kimi.log`:
  ```
  $ opencode run --model ruti-router/kimi
  === KILLED: ...opencode.CMD did not finish within 15s and was killed ===
  === stdout (partial) ===
  === stderr (partial) ===
  > build · kimi
  ```
- Таймаут здесь был всего 15с (видимо, тестовый прогон), но важно, что даже
  на простой генеративной задаче без сложного tool-use `opencode` не успел
  напечатать вообще ничего в stdout/stderr — только служебную строку
  `> build · kimi`.

## Наблюдение по всем трём случаям

- `ruti doctor` не показывает ничего криминального: прокси жив, TLS ок,
  `kimi` в списке моделей проксирования (`gemini-flash, gemini-flash-lite,
  kimi, local-*`). Проблема не в доступности бэкенда.
- `substituted: false` во всех случаях — значит фолбэк не срабатывал, ответ
  (когда он вообще был) шёл от настоящей `kimi`.
- Единственный "успешный" прогон (случай 2) занял всего 17.9с — подозрительно
  быстро для задачи, требующей прочитать и отредактировать 2 файла. Похоже
  на то, что `opencode` в этом случае вообще не сделал tool call (не читал
  файлы, не писал), а сразу текстом ответил на (пустой) промпт.

## Рабочая гипотеза

Похоже на баг на стыке `ruti delegate --task-file` → `opencode run`: либо

1. `ruti` передаёт `opencode` путь к файлу задачи, но `opencode` эту задачу
   не читает целиком (обрезание аргумента, неверный флаг, проблема с
   кодировкой кириллицы в длинном CLI-аргументе на Windows), либо
2. `opencode` при старте виснет на индексации репозитория (когда каталог
   большой/содержит много объектов `.git` или крупные файлы) ещё до того,
   как дойти до промпта — это объяснило бы случай 1 и случай 3 (зависание
   без вывода), но не объясняет случай 2, где `opencode` явно что-то
   ответил, просто не то содержимое.

Скорее всего это две разные проблемы:
- **Зависание** (случаи 1 и 3) — вероятно связано с запуском/индексацией
  `opencode` в конкретной директории (`--dir`), не зависит от размера
  задачи.
- **Потеря содержимого задачи** (случай 2) — отдельный баг в том, как
  `ruti delegate --task-file <path>` доставляет текст файла в `opencode
  run` (аргумент командной строки против stdin, экранирование, кодировка).

## Что стоит проверить при доработке

1. Как именно `ruti delegate` вызывает `opencode run` при `--task-file`:
   пробрасывает ли она путь как аргумент, читает файл сама и передаёт текст
   инлайн, или пишет во временный файл и передаёт его путь — и какой именно
   флаг/механизм ожидает `opencode` для длинных задач.
2. Повторить случай 2 с `opencode run` напрямую (без `ruti`), вручную
   передав тот же `task-20260809-144644.md`, чтобы понять, теряется текст
   на стороне `ruti` или на стороне `opencode`.
3. Проверить, зависает ли `opencode run --model ruti-router/kimi` при
   пустом/тривиальном промпте в маленькой директории (без `.git`) — если
   да, зависание связано с самой моделью/прокси, а не с индексацией
   репозитория.
4. Сравнить поведение `kimi` с `gemini-flash`/`gemini-flash-lite` на тех же
   трёх сценариях — обе тоже удалённые и бесплатные по квоте, это изолирует
   проблему конкретно до `kimi` либо покажет, что баг общий для всех
   удалённых executor'ов через `opencode`.
